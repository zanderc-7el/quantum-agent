01

概要

这套系统把超导量子芯片的校准做成一条可观察、可干预、可复盘的流水线。一次校准从创建工作流开始，按 Skill 定义的节点顺序推进；每个节点产生测量值，并与冻结在流程上的验收条件比较；达标就继续，不达标就按自主等级决定自动重试还是停下来等人。所有状态变化写入事件流，服务端保存权威副本。

当前实现是模拟闭环。保真度、T1/T2、读出频率等数值由时间模拟器生成，设备命令只做下发与回读校验，不连接真实测控机。这个边界在 UI 的页脚和接口响应里都有标注，阅读时先记住它，后面的“已实现”都以此为前提。

阅读约定

已实现 代码中存在，当前工作副本可运行。 模拟 功能闭环，但数据或设备是模拟的。 缺口 已识别、尚未闭环的问题，集中列在第 11 节。

三条结论

  1. 工作流的权威在 QuantaMind 服务端。前端内置模拟器是它的行为克隆，用于离线演示与契约对齐，不是第二套后端。
  2. 本机 5290 服务不是工作流后端。它只承担实验能力联调：S21 扫频、F01 频谱、参数候选与发布。界面上它属于“接口验证台”，不属于“蓝图版工作流”。
  3. 纵向链路已通，横向能力有缺口。创建、执行、异常、审批、完成、重启持久化都能走通；真实设备、CZ 执行、Skill 失败策略仍是未完成项。
02

总体架构

仓库里同时存在三个可独立启动的实体。它们看起来都在“跑校准”，但职责和权威性完全不同。先把这层关系说清，后面每个模块的设计才有落点。

2.1 三个运行实体

实体位置端口职责状态存放
前端工作台frontend/5286（Vite）视图、交互、权限展示、离线演示localStorage + IndexedDB
本机实验服务backend/5290配方预览、计划/运行、参数治理、模拟设备data/state.json
QuantaMind APIE:\work\QuantaMind18789（默认）工作流权威、Skill/设备版本、执行器、审计PostgreSQL 或 SQLite

2.2 权威边界

远程模式下，服务端是唯一的事实来源。每条命令携带 expectedRevision 与 requestId：前者防止用旧快照覆盖新状态，后者让重试不会重复执行。客户端收到 409 时拉取权威快照，最多自动重试一次；之后的变化通过 SSE 推送，而不是轮询。

前端模拟器与后端状态机的等价性是刻意维持的。后端 state_machine.py 的模块注释写明它是对 frontend/src/lib/simulator.ts 的逐行移植，要求同样的输入产生同样的节点顺序、进度数字和事件语义。这样做的好处是：离线演示与远程联调看到的行为一致，前端测试可以替后端契约兜底。代价是两边必须同步演进，任何一侧单独改判定规则都会破坏一致性。

2.3 技术栈

2.4 部署形态

开发态是三个进程：Vite 开发服务器、可选的 5290 实验服务、以及 QuantaMind API。生产态由 docker-compose 组织：PostgreSQL 16、执行迁移、启动 API；前端构建为静态资源单独托管。远程模式通过 VITE_GATEWAY_MODE=remote 与 VITE_API_BASE_URL 指定后端，构建时注入。

03

前端详细设计

前端是一个单页应用，没有 React Router，也没有 Redux。视图由 location.hash 决定，状态由 useWorkflowStore 与网关共同维护。这个选择让演示部署很轻，但也意味着深链接、浏览器历史和多标签页同步都要自己处理。

3.1 结构与启动

入口 main.tsx 挂载 App.tsx。组件层负责呈现与交互，lib/ 层承担状态、持久化、网关、权限和格式化。没有全局 store 库，跨组件状态通过 hooks 与 gateway 订阅传递。

lib/apiClient.tsHTTP 与会话sessionStorage、401 刷新、ApiError

3.4 本地状态与持久化

  • 工作区 key 为 qcal-workspace-demo-v1，最多 200 个任务；超限时拒绝写入并提示先导出。
  • 模拟推进按 4 秒/节点、每秒 25 个百分点计算；进度与尝试次数可复算，因此刷新后不会跳变。
  • 同一浏览器的多个标签页通过 storage 事件同步；没有服务端时，这是唯一的一致性机制。
  • 聊天记录与附件走 IndexedDB，工作区走 localStorage；两者生命周期不同，导出时分别处理。
  • 导入工作区会合并去重并返回新增/跳过计数，不覆盖已有任务。

3.5 远程适配

apiClient 把会话放在 sessionStorage：关闭标签页即失效，换标签页需要重新登录。请求遇到 401 会用刷新令牌换一次访问令牌，刷新失败才让用户重新登录。remoteGateway 在内存里维护工作流与 revision 的缓存，让 SSE 到达前的界面仍可渲染；审批与重试需要绑定到具体节点和尝试次数，缓存里保留了这份对应关系。

命令路径统一走 sendCommand：带 expectedRevision 与 requestId，收到 409 时先 GET 单条工作流拿到权威 revision，再重试一次；仍冲突就把错误交给界面。SSE 连接地址是 /api/v1/calibration/stream?token=...，支持 snapshot、workflow.updated、workflow.deleted 三类事件，断线后浏览器按 Last-Event-ID 续传。

安全提示

访问令牌放在 SSE 的查询串里，是因为浏览器原生 EventSource 不能设置请求头。代价是令牌可能进入反向代理访问日志、浏览器历史或监控采样。生产部署应限制日志对该参数的记录，或改用支持头的流式方案。

3.6 权限模型

界面权限只决定“按钮是否出现”，不是安全边界。真正的授权在服务端 RBAC。前端有 leader 与 operator 两种角色，再加上任务归属人。

3.8 前端侧已确认的问题

  • 远程模式冷启动时，如果服务端没有任何工作流，界面停在“正在连接工作空间”，只提供“重新加载”，没有创建入口。缺口
  • package.json 版本是 1.3.1，而 README 记录到 v1.7；README 说只有三个入口，实际已有 #api。文档与实现存在漂移。缺口
  • 报告导出把服务端测量也标成“模拟值”，对远程数据不准确。缺口
  • 会话放在 sessionStorage，新标签页不能共享登录态。这是取舍，不是缺陷，但需要在验收说明里写清。
04

本机实验模拟服务

backend/ 是一个零依赖的 Node HTTP 服务，用来在没有 QuantaMind、也没有真机的情况下演练实验能力。它有自己的计划、运行、事件和参数版本模型，但不参与校准工作流。把它误当成工作流后端，是联调时最常见的误解。

4.1 运行形态

  • 监听 127.0.0.1:5290，端口可用 QCAL_PORT 覆盖。
  • 状态写入 backend/data/state.json，路径可用 QCAL_DATA_FILE 覆盖；写入采用临时文件加替换，避免半写。
  • 每 250 毫秒推进一次处于 queued/running 的运行。
  • CORS 只放行 http://127.0.0.1:5286 与 http://127.0.0.1:5173。
  • QCAL_SIM_FAULT 可注入模拟故障，用于演练失败路径。
  • 没有鉴权。它只监听回环地址，定位是本机替身。

4.3 计划、运行与幂等

一个计划记录本次请求解析出的拓扑版本、参数版本、上游依赖和资源估计；预检通过后才允许启动运行。运行按尝试（attempt）产生事件与测量，客户端用 after 游标增量读取。

所有写命令接受 Idempotency-Key，长度 8–128 字符。服务端对请求体做摘要：同一键、同一摘要返回首次响应；同一键、不同摘要返回 IDEMPOTENCY_CONFLICT。参数候选的审批与发布另外校验基线版本，防止在旧参数上批准新值。

4.4 蓝图策略

蓝图不是 Skill，是能力范围：它限定一次任务可以请求哪些实验能力，并给出允许的目标比特。策略以版本号固定，超出范围直接拒绝。

蓝图版本允许能力目标
single1readout_resonator_scan、f01_spectroscopyQ12
two1上述两项 + cz_calibrationQ12 / Q13 / Q12-Q13

拒绝时返回 BLUEPRINT_VERSION_UNSUPPORTED 或 BLUEPRINT_SCOPE_DENIED。这条边界独立于 Skill 版本：Skill 定义“怎么做”，蓝图定义“允许做什么”。

4.5 确定性 Agent

Agent 端点只做规则化的计划预览与提案复核：给定目标与蓝图，产出步骤、依赖、缺口和风险提示；给定提案，检查范围、依赖与参数。响应固定 executable:false 与 modelUsed:false，不会下命令，也不会调用大模型。这样设计是为了让演示可复现，同时把“能看”与“能执行”分开。

4.6 参数治理

参数从测量走到发布要经过四道门：候选生成、审批、发布、回读校验。候选绑定来源运行、来源尝试、分析方法和产物摘要；发布要求候选已批准，且基线版本与期望版本都等于当前版本；发布后写入新 revision，回读不一致时结果不能视为已接受。回滚同样按 revision 做冲突检查。

4.7 本机服务的已知问题

  • 无鉴权、无角色，任何本机进程都能改状态；只适合回环地址下的联调。缺口
  • approveCandidate 先把候选状态改成 approved，再校验 actor；actor 非法时内存对象已被部分修改。应把校验提到赋值之前。缺口
  • 实施方案写计划初始状态为 draft，代码返回 preflight_passed，契约需要对齐。缺口
  • 双比特蓝图允许 cz_calibration，但本机模拟没有可执行配方，预览仍返回不可执行。缺口
05

QuantaMind 校准后端

这是系统的权威后端。它把校准工作流、Skill 与设备版本、执行器、账号与审计放在同一个 FastAPI 应用里，领域逻辑与 Web 层分离。状态机是纯函数，执行器在后台线程里推进，数据库保存每一次提交。

5.3 状态机

状态迁移集中在一个纯函数里：相同输入必然得到相同输出，非法动作返回原对象。命令层用“返回值是否为同一对象”判断是否发生了变更，再决定是否提交事务。

5.4 Skill 体系

Skill 是版本化的校准流程定义，包含节点顺序、每步的验收条件、设计目标、失败处理与自主等级。内置两套，版本均为 1.1.0。

双比特 CZ 校准two-qubit-calibration17完整单比特前置，加 Z 脉冲依赖、QQ 交换、CZ 扫描与精调、交叉熵基准、参数优化与复测

每步带验收条件；默认保真度门槛 0.98，T1 不低于 20μs，T2 不低于 10μs。验收条件与设计目标是两套数值：门槛回答“何时需要人看”，目标回答“离设计值还有多远”。把两者混在一起，会让 0.98 的验收下限看起来像设备的最好水平。

5.5 验收判定

判据以数据形式存在，不在状态机里写死。指标路径是点分隔的，允许 * 展开映射，例如 parameters.*.t1Us 会检查每个比特。所有解析出的值都必须满足比较；对“越大越好”取最小值作为 actual，对“越小越好”取最大值。指标缺失按失败处理，绝不当作通过。

判定结果连同当时使用的 Skill 版本、设备档案版本、判据、目标、实测值、样本数和决定一起写入评估记录。后续审计不依赖“今天的阈值”，也不依赖仍然活跃的注册表版本。

5.6 设备档案与冻结绑定

设备档案（M3/M5/M7/M8）可以覆盖 Skill 的默认判据与目标，例如不同机型对 T1 的要求不同。创建工作流时，Skill 与设备的版本、以及两者的完整定义会被冻结进绑定表；运行中的流程永远按冻结副本判定。这样即使管理员在运行期间激活了新版本，也不会改变在途任务的验收标准。

5.7 版本管理

状态含义可进入
candidate已发布，但未生效activate

superseded曾经激活，可再次激活作为回滚activate

内置 Skill 与设备档案是不可变的 Python 数据，数据库里的注册表是覆盖层。发布版本不修改内置定义，只新增一行；激活才改变新任务的绑定。

5.8 执行器与租约

  • 时间模拟执行器按每节点 4 个模拟秒、每秒 25 个百分点推进；调度 tick 默认 1 秒。
  • 后台循环可以多副本运行，但每轮只有一个副本能拿到数据库租约（默认 30 秒），避免同一工作流被推进两次。
  • 执行分 dry-run 与 live 两种设备控制语义；参数下发后做回读校验，校验不通过会把节点送进 ATTENTION。
  • 每次提交递增工作流 revision，并写一条全局流事件，供 SSE 断线续传。

5.11 认证、权限与审计

  • JWT HS256，访问令牌与刷新令牌分离；令牌内嵌 token_version，登出、改密、改角色、停用账号时递增，一次性吊销该账号的全部会话。
  • 口令使用 PBKDF2 哈希；开发模式会种入 leader 与 operator 两个演示账号，生产必须关闭 QUANTAMIND_DEV_AUTH 并更换所有凭据。
  • 角色为 calibration_leader 与 calibration_operator；审批、改策略、版本发布等动作限 leader，执行类动作限归属人或 leader。
  • 登录限流 10 次/60 秒，刷新 30 次/60 秒；单副本用进程内滑动窗口，多副本切换为数据库共享计数器。

5.12 后端侧已确认的问题

  • queued 与 failed 只出现在枚举、迁移条件与校验里，没有任何代码写入这两个状态。缺口
  • Skill 的 onFail 与 maxAttempts 只写进定义与评估记录，finish_node 不使用它们；L3 的自动重试没有次数上限。缺口

06

关键业务流程

6.1 创建工作流

创建请求包含名称、机型、比特数、目标、实验类型、策略、场景与蓝图。服务端校验目标与蓝图范围，生成节点列表（每个节点 pending），选择当前激活的 Skill 与设备版本，把两份完整定义冻结进绑定表，写入 revision 1，返回 draft。

POST /api/v1/calibration/workflows
{
  "name": "Q12 单比特校准演示",
  "machine": "M7",
  "qubits": 1,
  "target": "Q12",
  "type": "adaptive",
  "policy": "threshold",
  "scenario": "normal",
  "experiment": "single",
  "blueprintId": "single",
  "blueprintVersion": 1
}

蓝图校验发生在领域层之前：能力不在蓝图范围内时直接拒绝，不会产生半成品工作流。

6.2 启动与推进

  1. start 把第一个 pending 节点置为 running，attempt 加一，工作流进入 running。
  2. 执行器每次 tick 按经过的模拟时间增加节点进度；进度到 100 时产生测量值。
  3. finish_node 用冻结的 Skill 判据评估测量值；参数下发类节点还要检查回读。
  4. 判定结果交给策略：通过则继续下一个节点；失败则按 L1/L2/L3 分流。
  5. 最后一个节点成功后，工作流进入 completed，进度固定 100。

6.3 异常与人工决定

进入 attention 的节点带着评估记录与原因码：指标未达门槛、策略要求逐步确认、或没有可归因的记录。leader 可以接受结果，也可以重试。接受会把节点置为 success、记录“接受不代表达标”，然后继续；重试会把节点重置为 running、attempt 加一、清空后续节点的进度，并把工作流拉回 running。

L1（strict）对每个节点都要求确认，即使指标达标；L2（threshold）只在失败时停；L3（autopilot）在失败时自动调整参数并重试一次。当前 L3 的重试没有次数上限，这一点在第 11 节展开。

6.4 远程命令与断线恢复

6.5 重启与恢复

配置了数据库 URL 时，工作流、节点、事件与绑定都在库里。进程重启后：执行器重新抢租约，按节点进度继续推进；SSE 客户端带 Last-Event-ID 重连，服务端从全局流补发缺失事件；如果请求的序号早于保留窗口，则先发一份快照，再继续增量。未配置数据库时，存储退化为内存 SQLite，重启即清空，这是开发态的默认行为。

状态机与判定规则

7.1 工作流状态

状态进入条件可执行动作说明
draft创建完成start全部节点 pending
runningstart / resume / approve / retrypause / abort恰有一个 running 节点
pausedpauseresume / abort进度与计时冻结
attention失败或 L1 逐笔确认approve / retry / abort恰有一个 attention 节点
completed末节点成功—全部节点 success
abortedabort—未完成节点标记 abandoned
queued——枚举存在，当前无写入路径
failed——枚举存在，当前无写入路径

7.2 节点状态

状态含义迁移
pending尚未开始start / 前序完成后进入 running
running推进中完成 → success 或 attention；abort → abandoned
attention等待决定approve → success；retry → running
success完成且被接受终态
abandoned随工作流终止终态

7.3 结构不变量

每次提交前后都可以跑一遍校验，以下条件必须同时成立：

  • running / paused 恰有一个 running 节点；attention 恰有一个 attention 节点。
  • completed 的每个节点都是 success；aborted 只允许 success 或 abandoned。
  • success 节点必须构成列表前缀，不能留下中间的 pending。
  • draft / queued 只能包含 pending 且进度为 0 的节点。
  • 活动节点必须是第一个未完成节点。

7.4 自主等级

等级策略达标不达标
L1strict仍停在 attention，等人确认停在 attention
L2threshold自动继续停在 attention
L3autopilot自动继续自动重试；当前无次数上限

策略只影响未来的决定，不改写已经停在 attention 的节点。leader 改策略时会写一条事件说明这一点。

7.5 评估记录

一条评估记录包含 skillId、skillVersion、deviceId、deviceProfileVersion、节点、判据、目标与目标来源、实测值、是否通过、样本数、原因、决定和自主等级。它既是审计证据，也是回放输入：用同一份测量重放，应当得到同一个结论。

  1. 先把演示闭环做稳。补启动页创建入口与服务端种子；统一文档版本；修正导出标注。目标是一次冷启动可以从零走到完成。

蓝图一次任务允许请求的实验能力与目标范围，不等于 Skill
读回校验参数下发后重新读取设备值，与期望值比对
revision工作流提交版本，用于乐观并发控制
requestId命令幂等标识，重试时复用
